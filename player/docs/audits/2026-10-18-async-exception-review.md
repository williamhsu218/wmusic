## 已修复的问题

| 范围 | 原有故障 | 修复与回归证据 |
|---|---|---|
| 播客搜索超时 | 用结构化任务组竞争网络与计时器，即使计时器先结束，退出任务组仍须等待不响应取消的网络子任务 | `OperationDeadline` 让调用方的等待有界；取消、注册、完成竞争只恢复一次 continuation。默认每个搜索源 8 秒；详情查询也有期限并能进入备用源。用忽略取消的 HTTP 替身验证 |
| 播客失败与回退 | 未配置 Podcast Index 被视为一个成功的空来源，掩盖唯一来源 iTunes 的失败；已配置的主来源失败后没有执行详情回退 | 仅统计已配置来源；全部失败明确报错；主来源失败、空结果或超时后尝试 iTunes；取消保留取消语义 |
| 音频操作串行化 | `load` 没有经过播放控制互斥门；已取消的排队操作仍可能在稍后执行 | 加载与播放、暂停、停止、拖动共享 FIFO 门；取消移除等待者，交接期间不允许后来者抢先。回归包含持锁加载和取消排队播放 |
| Subsonic 下载缓存 | URL 签名失败可能遗留其他等待者；签名或流停滞没有统一退出；旧下载的迟到失败可能删除重试结果 | 等待者分别可取消并共享下载；最后一个等待者离开时清理；默认连续 30 秒无进展失败；签名、响应头和有效数据刷新期限；条目及计时器代号隔离迟到回调。同时防止预算淘汰刚返回的文件，单个大文件可暂时超过软预算。验证共享请求、停滞、重试、持续慢速传输和超预算文件 |
| HTTP 取消竞争 | 在 response continuation 注册前收到取消/错误，可能丢失终态并一直等待 | 在锁内保存终态；迟到注册立即失败；取消直接恢复等待者并取消底层请求。用确定性委托调用覆盖两个注册前终态 |
| 延迟恢复行为 | 首次播放前拖动仍直接调用空引擎；未加载的播客在退出时可能把有效进度覆盖成 0；加载失败可能漏释放文件安全作用域 | 未加载时只保存播放意图；显式拖动优先于播客保存点；区分队列选中项与引擎真正加载的项；播客使用逐集进度；安全作用域由 `defer` 释放。已加载时仍以解码器时长为准，避免陈旧曲库元数据阻止合法拖动 |
| 同步服务生命周期 | 启动中停止没有完整撤销已启动组件；监听回调卡住没有期限；停止监听并未关闭已建立连接 | 合并并发启动、串行停止、取消并等待启动清理；监听就绪期限 10 秒；跟踪并关闭存量连接，忽略旧监听代号的接入回调。用本机 TLS、挂起回调队列和启动/停止竞争验证 |
| 音频指纹子进程 | 先等待进程退出再读管道，大量输出会阻塞；无超时/取消清理 | 临时文件承接输出；异步接收退出；默认 60 秒期限；取消先终止，200 ms 后仅对仍存活的自有子进程强制结束。测试大 stderr、挂起及忽略 TERM 的子进程 |

共同期限工具只保证调用方及时返回；底层工作取消仍取决于其实现。因此缓存另有代号校验，指纹计算另有子进程回收。没有把“Task.cancel 已调用”当作资源已释放。
